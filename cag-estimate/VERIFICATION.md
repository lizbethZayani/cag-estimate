# CAG Estimate - Verification Pipeline

This document describes the verification pipeline for validating project estimations generated by the CAG Estimate API.

## Overview

The verification pipeline ensures that all project estimations are:
1. **Valid**: Correct JSON structure and all required fields
2. **Accurate**: Mathematical calculations are correct
3. **Reasonable**: Values fall within realistic ranges
4. **Coherent**: Content is meaningful and consistent
5. **Logical**: Related fields align with each other

## Validation Rules

### 1. Schema Validation
Ensures the response has correct structure:
- `estimation` object with project details
- `model` and `provider` fields
- `tokens_used` with input/output/total
- `cost_breakdown` with cost details
- Each task has required fields
- Summary has all required fields

**Status:** ✅ Validates all structural requirements

### 2. Business Logic Validation
Verifies calculations are mathematically correct:
- `total_hours = sum(task hours)` (±15% tolerance)
- `total_cost = sum(task costs)` (±5% tolerance)
- `cost ≈ hours × hourly_rate` (within tolerance)
- `duration ≥ total_hours / (40 hours/week × team_size)`

**Tolerances:**
- Hours: 15% or minimum 10 hours
- Cost: 5% or minimum $50

**Status:** ✅ Detects calculation errors

### 3. Reasonableness Validation
Checks values are within realistic ranges:
- Task count: 3-20 tasks per project
- Project hours: 8-500 hours
- Hourly rate: $30-$150/hour
- Complexity ranges:
  - Simple: 4-12 hours
  - Medium: 10-32 hours
  - High: 16-56 hours

**Status:** ✅ Flags outliers and unrealistic estimates

### 4. Content Quality Validation
Ensures descriptions and documentation are meaningful:
- Project name: 5-100 characters
- Task descriptions: 20-500 characters each
- Includes list: 2-15 items per task
- Meeting summary: 50-2000 characters
- Assumptions: 3-20 assumptions, each 10+ characters

**Status:** ✅ Ensures documentation quality

### 5. Consistency Validation
Verifies logical coherence between fields:
- Complexity aligns with hours (Simple <16h, High >14h)
- Team size is reasonable for project hours
- Task IDs are unique and sequential
- Duration matches team size and hours

**Status:** ✅ Detects logical inconsistencies

## Manager's Confidence Levels

### ✅ GREEN - Estimation Approved
All validations pass. The estimation is:
- Mathematically correct
- Within reasonable ranges
- Logically consistent
- Well-documented

**Action:** Proceed with estimation

### ⚠️ YELLOW - Review Required
Some validations show warnings but not critical errors:
- Minor calculation tolerance exceeded
- Task complexity slightly mismatched
- Assumptions could be clearer

**Action:** Review with team and adjust if needed

### ❌ RED - Estimation Rejected
Critical validation failures:
- Major calculation errors
- Unrealistic values
- Missing or invalid data
- Inconsistent team/timeline

**Action:** Request new estimation or fix manually

## Integration with Manager Workflow

1. **Project Meeting** → Manager captures transcription
2. **API Call** → Submit transcription to `/api/v1/estimate`
3. **Verification** → Automatic validation pipeline runs
4. **Status Report** → Green/Yellow/Red confidence level
5. **Decision** → Approve, review, or reject estimation
6. **Archival** → Store estimation and verification result

## Troubleshooting

### Validation Failures

**Problem:** "Total hours mismatch"
**Solution:** The LLM may have made a calculation error. Check if all tasks are properly listed and hours add up correctly. The 15% tolerance should catch most variations.

**Problem:** "Task marked High but has low hours"
**Solution:** The complexity label doesn't match hours. This could indicate either the label is wrong or the estimate is underestimated. Review with the estimation team.

**Problem:** "Hourly rate too high"
**Solution:** The estimated hourly rate exceeds $150. This may be for specialized senior developers, which is valid but should be verified.
